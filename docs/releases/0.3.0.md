# Vatrushka 0.3.0

Version 0.3.0 completes the design-system-to-stabilization roadmap while preserving quick rooms and the existing self-hosted deployment model.

## Highlights

- The desktop client now has a unified dark visual system, responsive server navigation and regression-tested critical screens.
- Voice exposes real input/output device selectors, individual participant volume and local mute without affecting anyone else.
- Screen sharing distinguishes monitors from application windows, lets the presenter choose system audio before capture and lets every viewer control stream audio separately. Windows loopback requests exclusion of Vatrushka's own output to avoid duplicated participant voices.
- Servers include text/voice channels, direct messages, role hierarchy, channel-specific inherit/allow/deny overrides and an audit log. API checks remain authoritative and LiveKit grants restrict speaking and screen/audio publication.
- Authentication supports password registration, email/TOTP second factor, recovery codes, trusted devices, active-session revocation and security activity. Refresh tokens remain in Electron main/safeStorage and are not exposed through preload.

## Upgrade from 0.2.0

1. Back up PostgreSQL and keep the previous API image or commit available.
2. Pull the 0.3.0 source and verify environment variables against `.env.example` and `apps/desktop/.env.production.example`.
3. Run `npm ci`, `npm run db:check`, `npm run test` and `npm run build` on the release source.
4. Deploy the API. Its startup command applies all pending Drizzle migrations before opening the HTTP server.
5. Verify `/health/ready`, password/email login, the Sessions security tab and access to an existing server.
6. Build the Windows client with the production `VITE_PUBLIC_API_BASE_URL`, then run `npm run package:win` and distribute both 0.3.0 artifacts as appropriate.

All existing migrations are retained. The 0.3.0 sequence is additive; do not delete, edit, renumber or squash migrations already recorded by a server. `npm run db:check` validates the journal, SQL files and snapshot chain without connecting to PostgreSQL.

## Rollback

Stop the 0.3.0 API, restore the previous application image/commit and start it against the same database. Additive tables and columns can remain in place and are ignored by the older API. Database restoration is required only if an operator independently performs a destructive/manual schema or data change; the application does not attempt automatic down migrations.

Desktop clients do not auto-update, so keep the previous installer available until the two-machine media matrix is complete.

## Verification checklist

- `npm run lint`, `npm run typecheck`, `npm run test`, `npm run db:check`, `npm run build` and `npm run perf:check` pass;
- Storybook interaction/a11y, Electron E2E and Windows visual regression pass;
- real Windows input/output switching works before and during a voice session;
- two clients validate independent microphone and screen-audio volume/mute;
- monitor and application-window sharing work with and without audio, and tracks disappear after stop/leave;
- denied roles cannot read/private-channel operations, join voice, speak or publish screen/application audio;
- an active session can be revoked and recovery codes are single-use;
- UI remains usable at Windows scaling 100%, 125% and 150%.

## Known limitations

- real SMTP delivery, NAT/TURN and Windows capture cannot be fully reproduced by CI and require the manual release matrix;
- text and presence updates still use polling rather than a realtime socket;
- server moderation has kick but no persistent ban list;
- installers are unsigned, and release channels/automatic updates are not implemented.
